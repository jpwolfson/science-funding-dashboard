### HIGH-5 — Published period series contain fabricated multi-billion swings from empty File B snapshots

Found by the reader review (cumulative lines "collapsing to zero mid-year")
and traced to the data, not the chart. `obligation_common.aggregate` derives
period activity by differencing successive cumulative File B snapshots. When
a period's download returns an empty or near-empty file, the adapter accepts
it (status row count == parsed row count holds for 0 == 0 and 1 == 1), so the
cumulative-through-period value becomes ~0 and the published period activity
becomes a huge negative followed by an equal positive the next period.

| Account | FY | Period with empty snapshot | File B rows (prev → this → next) | Published cumulative (prev → this) |
|---|---|---|---|---|
| dod/navy-rdte | 2025 | P11 | 239 → **1** → 243 | $23.0B → $0 |
| dod/air-force-rdte | 2025 | P11 | 221 → **1** → 227 | $45.8B → $0 |
| dod/army-rdte, dod/defense-wide-rdte, dod/defense-health-program, dod/space-force-rdte | 2025 | P11 | same pattern | $19.2B / $30.1B / $38.8B / $16.7B → $0 |
| commerce/noaa-orf, commerce/noaa-pac | 2024 | P09 (P02–P11 all ≤10 rows; P12 = 551) | — | $0.7B / $0.8B → $0 |
| commerce/nist-its | 2025 | P11 | — | $5.7B → $0.7B |
| dod/air-force-rdte | 2024 | P05 | — | $14.0B → $0.03B |

Scan: 8 account-years with a cumulative point of exactly $0 after a positive
value; 5 more with a >50 % drop. Every FY total still reconciles to GTAS
because P12 is correct, so the exact-cents gate is blind at period grain.
What readers see: "Obligations by reporting period" on the landing page shows
≈−$180B then ≈+$230B at 2025P11–P12; each DoD page shows a −$20–46B month;
NOAA's FY2024 cumulative line rises to $4.4B and falls to $0.7B. These are
publishable numbers a reader could cite as deobligations that never happened.
`File C + residual = File B` still holds at every grain — the residual
absorbs the artifact — which is why no validator caught it. Fix requires a
snapshot-acceptance rule (a period snapshot with fewer rows than the prior
period's, or zero rows after a populated period, is "not yet reported", not
"cumulative zero"), a re-pull of the affected account-years on CI, and an
owner decision on how a not-yet-reported period is displayed (gap vs
hold-last). Until then the period charts on DoD, NOAA, and NIST pages, and
the landing page, are wrong at period grain.

## Recommendation (option memo)

The engagement rule is that severity-high findings hold Stage 2. Options:

A. **Repair the operating state first, then re-review, then Stage 2**
   (recommended). Work items, all engineering-layer except where noted:
   1. Replace the exact-evidence NIH exclusion/retraction pins with a
      tolerant, retained-record contract: a returned or re-dated record is
      retained (never a warning-to-error), the ledger records the return,
      and only a *net* shrink without ledger cover fails. This is a
      data-integrity design change and needs an owner decision on measure
      semantics (which date a re-dated NIH award is counted under).
   2. Stop the sentinel and obligation workflows from running the NIH unit
      suite as a publication gate (run only their own contract tests +
      `validate_obligations`/`validate_funding_sentinel`).
   3. Land P10 for the nine pending accounts (or retire the retry manifest
      and revert the six empty PA identities and the DHS P10 pin) so
      validation is green without the hatches.
   4. Publish the DoD interpretation note on DoD account/PA pages and the
      agency row — wording to the owner for sign-off, per the standing norm.
   5. Rebuild NIH/root rollups once validate-nih is green; confirm one
      scheduled green run of each of the three workflows with the
      53-account registry.
   6. Add the File B snapshot-acceptance rule from HIGH-5, re-pull the
      13 affected account-years on CI, and decide (owner) how a
      not-yet-reported period is displayed.
   Then re-run this review's mechanical tiers and proceed to Stage 2.
B. Accept the closeout as-is, record the soak gate as waived by the owner,
   and run Stage 2 now. Not recommended: Stage 2's reader review would be
   run against a site whose root page is stale and whose sentinel is 21 days
   old, and every Stage 2 chart screenshot would be taken from a tree that
   fails the fast tier.
C. Run Stage 2 in parallel with repairs on a separate branch, merge only
   after A completes. Reasonable if the owner wants display work to start
   now; the batch's own evidence must then be regenerated after the repairs.
